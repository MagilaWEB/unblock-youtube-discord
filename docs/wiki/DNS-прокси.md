# 🌐 DNS-прокси

Провайдер фильтрует не только трафик, но и DNS: подменяет ответы, отдаёт «заглушки» или просто не резолвит заблокированные домены. DNS-прокси в Unblock забирает системный DNS себе и уводит запросы в шифрованные резолверы (DoH/DoT) в обход провайдерского. Заодно через него работают региональные ограничения — ответы приходят от зарубежного резолвера.

Внутри — библиотека [AdGuard DnsLibs](https://github.com/AdguardTeam/DnsLibs), собранная в `bin/AdguardDns64.dll` (Apache License 2.0). Служба `unblock_dns` запускает `bin/unblock_dns.exe`, который слушает DNS локально и держит наш резолвер как единственный источник ответов.

## Что происходит при включении

1. Приложение пишет конфиг `user/dns_proxy.conf` из настроек вкладки DNS.
2. Поднимается служба `unblock_dns`, прокси слушает `127.0.0.1:53` по UDP и TCP, а если в системе доступен IPv6-loopback — ещё и `[::1]:53`.
3. Адаптеры, у которых есть маршрут по умолчанию (то есть через которые реально идёт трафик), переключаются на `127.0.0.1` и `::1`. Туннельные и loopback-адаптеры не трогаются — сломанный DNS на VPN-адаптере только порвал бы связь.
4. Прежние адреса DNS каждого адаптера сохраняются в `user/dns_proxy.adapters`. Кэш резолвера сбрасывается.
5. Всё, что система резолвит дальше, идёт через прокси — включая хосты, которые движок обхода только собирается резать.

Первое включение сопровождается окном-согласием: приложение меняет системный DNS, и об этом честно спрашивают. Ответ запоминается.

## Резолверы

Список серверов задаётся на вкладке DNS («🌐 DNS-серверы») и в `configs/dns_proxy.config`, секция `[DEFAULTS]`. **Порядок — это приоритет**: первый адрес становится основным резолвером, остальные работают только как запасные. По умолчанию первым идут DoH-эндпоинты [GeoHide DNS](https://dns.geohide.ru:8443), потому что региональные ответы нужны именно от него:

```
upstream=https://geohide.ru/dns-query;https://eu.geohide.ru/dns-query;https://us.geohide.ru/dns-query;5.175.161.3;…;https://dns.zapret.moe/dns-query
bootstrap=1.1.1.1;8.8.8.8;9.9.9.9;77.88.8.8
timeout=5000
```

Поддерживаются схемы адресов `https://` (DoH), `tls://` (DoT), `quic://` и `h3://` (DoQ/HTTP-3), `sdns://` (DNS-stamp), `tcp://`, а также обычный IP. **Bootstrap** — это простые DNS-серверы, которыми резолвятся имена самих шифрованных апстримов; апстрим с именем без bootstrap отклоняется. Если провайдер портит и bootstrap, укажите там адрес, который у вас открывается.

Таймаут обмена по умолчанию — 5000 мс. Рядом кнопка проверки апстрима: она запускает `unblock_dns.exe --test-upstream-file` и показывает `OK` или причину отказа.

## Свои hosts-пины

Второй механизм — прямые пины «домен → IP». Файлы `configs/dns_hosts/*.list` содержат строки вида:

```
updates.discord.com->162.159.138.232
instagram.com->157.240.0.174
```

При включении DNS-функции эти пины собираются в файл `user/hosts_user.list` и подмешиваются к системному `hosts` (рядом хранится резервная копия `hosts_backup`). Так домен принудительно идёт на заданный адрес, минуя любой резолвер. Часть списков идёт с готовыми пинами (Discord, Facebook, Instagram, Rutor), остальные — только с комментарием-примером, их можно заполнять самому.

## Состояние и логи

Строка статуса на вкладке DNS показывает, что происходит:

- `🌐 DNS-прокси работает · запросов: N · из кэша: N · ошибок: N`;
- `⏸ DNS-прокси работает, но не применяется: активен VPN-туннель «имя»` — под VPN прокси не нужен, адаптеры возвращены системе;
- `⚠ DNS-прокси — <причина>` — служба не поднялась, по клику открывается [отчёт диагностики](Отчёт-диагностики).

Рабочий лог прокси лежит в `user/dns_proxy.log`, бэкап адаптеров — `user/dns_proxy.adapters`.

## VPN и аварийное восстановление

Как только поднимается VPN-туннель, прокси отдаёт адаптеры обратно (под туннелем всё равно работают его резолверы) и забирает их снова, когда туннель уходит. Определяется это по адаптерам и маршрутам, вручную ничего делать не нужно.

Если службу убили жёстко (краш, снятие процесса), восстановление делается при следующем запуске приложения: `repairBoot` видит оставшийся `dns_proxy.adapters` и вызывает `unblock_dns.exe --repair`, который возвращает адаптерам их адреса из бэкапа. Тот же механизм отрабатывает при штатной остановке.

## Свой резолвер: пошагово

1. Откройте вкладку DNS и добавьте адрес в список 🌐 DNS-серверов. Порядок задаёт приоритет: первый — основной, остальные запасные.
2. Проверьте адрес кнопкой проверки апстрима — она покажет `OK` или причину отказа (плохой формат, нет bootstrap и т.п.).
3. Если апстрим задан именем (`https://dns.example/dns-query`), убедитесь, что в поле bootstrap есть хотя бы один рабочий простой DNS-адрес: без него шифрованный апстрим не зарезолвится.
4. Примените — приложение перепишет `user/dns_proxy.conf` и перезапустит прокси.
5. Гляньте `user/dns_proxy.log`, если что-то не поднялось: там видно, какие слушатели и апстримы инициализировались.

> [!NOTE]
> Внутри прокси слушает `127.0.0.1:53` (и `[::1]:53`, если IPv6-loopback доступен) по UDP и TCP. Порт 53 выбран сознательно — так Windows и приложения ходят в DNS без дополнительных настроек.

## Как выключить и вернуть всё назад

Снимите галочку 🔒 **DNS-прокси** — приложение остановит службу, вернёт адаптерам прежние DNS из бэкапа и уберёт hosts-пины. То же произойдёт по кнопке ⏹ **Остановить все службы** и при удалении приложения.

Если после ручного вмешательства адаптеры остались с адресом `127.0.0.1`, запустите приложение один раз: аварийное восстановление отработает по оставшемуся бэкапу. Полностью убрать систему «в ноль» можно, вернув на адаптерах «Получить адреса DNS автоматически».
