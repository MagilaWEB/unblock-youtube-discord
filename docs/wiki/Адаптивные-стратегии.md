# 🧠 Адаптивные стратегии (auto_strategy)

`auto_strategy` — Lua-скрипт `binaries/lua/unblock_auto_strategy.lua`, который работает внутри `winws2.exe` и перебирает стратегии обхода прямо на живом трафике. Никакой ручной выбор профиля тут не нужен: скрипт сам решает, какая стратегия подходит конкретному хосту у конкретного провайдера прямо сейчас.

В Unblock есть два уровня перебора, и их легко перепутать:

- **Автоподбор конфигураций** (кнопка ⚙️) — перебор целых конфигов и наборов. Для Zapret2 он пассивный: помощник проверяет хосты через работающий движок, а Lua ставит вердикты. Успех — 90% рабочих хостов, провал — если мёртвых больше 10%.
- **`auto_strategy`** — перебор стратегий **внутри** одного конфига. Именно про него эта страница.

## Как это работает

1. **Прямой трафик первым.** Новое соединение начинается со стратегии `direct` (номер 0) — попытка пройти без обхода. Если в конфиге задан `start=N`, прямой этап пропускается и перебор стартует с номера N.
2. **Последовательный перебор.** На провале берётся следующая стратегия из плана: `strategy_1`, `strategy_2`, … `strategy_N`. Соединение докладывает о провале не чаще раза в 2 секунды, чтобы одно залипшее рукопожатие не сожгло весь порог ретрансмиссиями.
3. **Запоминание рабочей.** Подтверждённая стратегия набирает очки и хранится в памяти вместе с замеренной скоростью и охватом по хостам. При переподключении того же хоста перебор идёт с учётом этой статистики, а не с нуля.
4. **Все исчерпано** → хост паркуется на лучшей замеренной стратегии и уходит в кулдаун на `time` секунд; `helper` получает пометку, что хост полностью перебран.

Память — **в пределах текущего прогона `winws2`**. Перезапуск движка очищает статистику: подтверждённые стратегии придётся набрать заново.

## Кто судья, а кто насос

Вердикт ставит **только Lua**, по пакетным уликам. Помощник вердиктов не выносит — он насос: по команде `CHECK:<host>` открывает свежее соединение к хосту через текущую стратегию и гонит трафик, чтобы у Lua появились новые пакеты. Положительный вердикт `VALID` рождается из ответа сервера, а не из факта, что curl у помощника завершился успешно. Подробности про порты и состояния — в [zapret-helper](zapret-helper).

Lua просит `CHECK` только на TCP и не чаще раза в 5 секунд на запись хоста. UDP помощник не проверяет вообще — UDP-логику Lua ведёт сама.

## Улики блокировки

**TCP:**

- **Ретрансмиссия** пакета с данными **до** ответа сервера — застрявшее рукопожатие (DPI пропустил запрос и срезал ответ). Ретрансмиссия на соединении, где сервер уже ответил, обычная потеря и провалом не считается.
- **RST** приходящий в начале рукопожатия (seq 1..8192) — DPI срезал соединение.
- **DPI-redirect**: ответ `302`/`307` ведёт на чужой хост — подмена.
- **Троттлинг после рукопожатия** (только потоковые хосты, см. ниже): два плохих окна скорости подряд.
- **Тишина после рукопожатия** (`SILENCE TCP`): клиент переспрашивает, сервер молчит `tcp_silence` секунд, а объёма для замера скорости поток не набрал. Это единственная улика для мелких потоков — рукопожатие прошло, ответа на запрос нет. Одного тихого окна мало: вердикт ставится, только когда клиент долбит через `tcp_silence_windows` окон подряд, а сервер молчит всё это время. Естественное молчание — плеер между сегментами, догруженная страница, удержанный запрос — новых пакетов клиента в окно не добавляет: серия обрывается, и рабочее соединение не рвётся. Потоковых семейств это не касается: у них вердикт по-прежнему с первого окна — там стопор означает остановившееся видео, и второе окно оплачивает зритель.
- **Нет прикладных данных после запроса** (`SILENCE TCP`): рукопожатие прошло, клиент отправил запрос, а приложение так и не ответило `2 × tcp_silence` секунд — один вердикт на соединение. Такое соединение **не подтверждается**: рукопожатие без данных — не ответ, иначе оно обнуляло бы серию провалов, и приложение висело бы минутами на «рабочей» стратегии. Long-poll, получивший заголовки, под это правило не попадает: у него уже есть прикладные данные. Для direct два вердикта `SILENCE TCP` за окно `time` означают немедленный уход на другую стратегию: успешные direct-соединения между ними этот отдельный счётчик не обнуляют, а признак `direct_ok` снимается, чтобы direct не вернулся в начало кандидатов. У desync-стратегий остаётся обычный порог `fails`, чтобы медленный, но рабочий сервер не гонял перебор.

**UDP** (`STUN`, `WireGuard`, игровой UDP): успех — новые пакеты сервера, провал — `udp_out` исходящих подряд без ответа. Плюс правило тишины: клиент продолжает слать, сервер молчит `udp_silence` секунд — провал. У потокового UDP (`QUIC`) пакетный счётчик провал не ставит: клиент подтверждает свой бурст, а сервер молчит между сегментами, и это нормальная форма загрузки, а не мёртвая стратегия. Его судят скорость и тишина. Голосовой план помечается `udp_voice=1`: там после первого ответа сервера пакетный счётчик поток не судит вообще — в тихом голосовом канале сервер молчит, пока никто не говорит, и это не повод валить рабочую стратегию. Мёртвая стратегия видна до первого ответа (клиент шлёт, сервер не ответил ни разу); если путь умер позже, клиент переподключится, и новый поток снова пройдёт ту же проверку. Долгоживущие потоки (голос, WireGuard) перебирают стратегии без переподключения.

### Почему видео судится по скорости

Обычный TCP подтверждается ответом сервера — для API и long-poll этого достаточно. А вот потоковые хосты (`googlevideo.com`, медиа-CDN `fbcdn.net`) и QUIC так судить нельзя: «сайт открылся, видео стоит» — типичный троттлинг. Поэтому потоковый хост подтверждается только здоровым окном скорости (два хороших окна подряд выше `throttle_min_bps` и без резкого падения относительно пика соединения). Окно без серверных байт — провал только если клиент продолжает просить данные: если клиент тоже молчит (буфер подхвачен, качать нечего), это пауза, а не обрыв, и окно вообще не судится — база стратегии при этом не меняется. Обвал относительно пика судится только ниже `throttle_collapse_floor_bps` — но это запасное правило для хоста, где ещё ничего не замерено: одна и та же полка 150 КБ/с на одном линке норма, на другом стопор. Как только замерена другая стратегия, обвал считается от неё: окно медленнее лучшей альтернативы в 1/`throttle_collapse` раз — обвал при любой абсолютной скорости, пол уже не нужен. Сравнение идёт по последнему окну каждой стратегии (`last_rate`), а не по рекорду: если альтернатива тоже оказалась медленной, её база падает и перебор прекращается — одинаково ползущие стратегии означают потолок линка, а не виноватую стратегию. Обвал решает судьбу потока сразу, без накопления серии провалов: каждая новая сессия плеера начинается с бурста, два хороших окна подтверждают ту же стратегию и обнуляют серию, так что рвущийся поток иначе не переехал бы никогда. Для потока, который сервер закрыл, не набрав объёма (короткая проба), вердикт всё же даёт ответ сервера. У googlevideo по QUIC порог объёма ниже (`udp_stream_min_bytes`): проб хелпера по HTTP/3 нет (curl умеет только TCP), поэтому любой объём там — само видео, и ждать 200 КБ, пока поток ползёт, незачем.

## Перебор и запоминание

Кандидаты на следующую стратегию берутся в таком порядке: подтверждённые — сначала по замеренной скорости, затем по числу хостов, где стратегия себя показала, затем по числу успехов; следом неотмеченные — начиная с тех, что реже всего падали у других хостов плана. Так разбор сходится на нескольких широко рабочих стратегиях, а не размазывается по всему плану.

`direct` — такая же стратегия, как остальные, только с номером 0: в рейтинг он не пишется, поэтому хост, который ответил напрямую, запоминается отдельным признаком и держит `direct` во главе своих кандидатов, пока тот работает. Иначе хост, которому обход не нужен, после первого же сбоя уезжал на дез-стратегию и начинал подмешивать фейки в рабочее соединение. Провалившийся `direct` уходит из головы списка и возвращается только после полного круга. Потоковых семейств это не касается: у них выбором владеет замер скорости, а удачное окно на `direct` доказывает только то, что шейпер пропустил первый бурст, — поэтому видео после сбоя, как и раньше, уходит на дез-стратегии. Зоны из `no_direct` (`discord.media`, `gateway.discord.gg`) не получают `direct` ни в начале, ни после исчерпания плана: они блокируются целиком, и пробовать на них прямое соединение — только терять время на заведомо мёртвую попытку. Гейтвей в списке не случайно: у него direct подтверждается отдельными HTTPS-соединениями, а веб-сокет приложения на нём виснет, поэтому он тоже стартует со стратегии, а не с прямого.

Хост, который уже срабатывал, ротируется по успешным, но после двух полных кругов без успеха выходит в полный перебор. Стратегия, которая работает, — тоже не финал: если найдена замеренно более быстрая, семья переезжает на неё.

Стратегия считается **на план и на прогон**: номера стратегий в разных профилях означают разное, поэтому записи разделены отпечатком плана (набор его номеров стратегий) и протоколом (TCP/UDP живут отдельно). Общие зоны задаются один раз при старте: `templates.config` вызывает через `--lua-init` функцию `unblock_host_policy[[stream=googlevideo.com,c.youtube.com,fbcdn.net;group=discord.media]]`, которая пишет списки в `_G`. Поэтому вся семья `*.discord.media` делит запись `group.discord.media`, а медиа-хосты из `stream=` судятся по скорости независимо от профиля. Корень `discord.media` остаётся отдельным. Без этого вызова скрытых списков хостов и группировки в Lua нет.

## Голос Discord

Для голоса в конфигах заведён отдельный план UDP-голоса (`START_VOICE`), а TCP-фаза идёт обычными TLS-стратегиями. Порты берутся из `configs/service_setting.config`: `DiscordPort` (TCP) и `DiscordPortUPD` (UDP, пул Cloudflare + пул Google Cloud). Хосты голоса проверяются особым образом, а записи по сырым IP разделяются классом протокола — STUN браузера и `discord_ip_discovery` десктопа не смешиваются. Голос работает и в браузере, и в десктопном приложении.

## Параметры

Задаются в строке `--lua-desync=auto_strategy:...`. Например, в `strategy_super_c`: QUIC-план — `start=1:fails=6:time=90:udp_out=8`, TLS-план — `fails=3:maxseq=32768:reset:no_direct=discord.media,gateway.discord.gg`, голосовой план — `fails=6:start=1:udp_voice=1`. Общие `stream=` и `group=` здесь не повторяются: их один раз записывает `--lua-init=unblock_host_policy[[...]]` из `templates.config`.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `fails=N` | 3 | провалов до переключения |
| `time=N` | 60 | окно сброса счётчика провалов и кулдаун после исчерпания, сек |
| `maxseq=N` | 32768 | максимальный seq для проверок ретрансмиссии |
| `throttle_window=N` | 3 | окно замера скорости, сек |
| `throttle_min_bps=N` | 50000 | порог скорости, Б/с; ниже окно считается плохим |
| `throttle_collapse=N` | 0.25 | доля пика, ниже которой окно плохое (0 — выключить) |
| `throttle_collapse_floor_bps=N` | 100000 | выше этой скорости падение относительно пика — полка, а не обвал (0 — судить любое падение) |
| `throttle_windows=N` | 2 | сколько плохих окон подряд до провала (обвал ниже `throttle_collapse_floor_bps` решает сразу) |
| `stream_min_bytes=N` | 200000 | объём серверных байт, с которого поток считается потоковым |
| `udp_stream_min_bytes=N` | 16384 | тот же порог для потокового хоста на QUIC: проб по HTTP/3 нет, объём там — само видео |
| `udp_out=N` | 4 | исходящих UDP-пакетов до вердикта FAIL |
| `udp_in=N` | 1 | входящих UDP-пакетов для успеха |
| `udp_silence=N` | 3 | секунд молчания сервера при живом исходящем потоке |
| `tcp_silence=N` | 5 | то же для TCP (0 — выключить) |
| `tcp_silence_windows=N` | 2 | тихих окон подряд до вердикта `SILENCE TCP` (у потоковых семейств — 1) |
| `reset` | выкл | слать RST при переключении |
| `start=N` | 0 | начальный номер стратегии (0 = direct) |

## Как читаются логи

В логе unblock сообщения Lua приходят с префиксом `zapret:auto_strategy:`:

```
zapret:auto_strategy: CONFIRMED TCP strategy_3->www.youtube.com:443
zapret:auto_strategy: FAIL strategy_3 is_retransmission->discord.com:443
zapret:auto_strategy: SWITCH strategy_3->strategy_7 www.youtube.com:443
zapret:auto_strategy: THROTTLE strategy_3 18000B/s peak=940000->rr1---sn-....googlevideo.com:443
zapret:auto_strategy: SILENCE strategy_5->....:443 out=12 in=0
```

Имя стратегии в логах — `direct` или `strategy_N`, а не безликий номер. Уровни: `CONFIRMED` и `SWITCH` — успех, `FAIL`, `THROTTLE`, `SILENCE` — провал с указанием причины. В `binaries/winws2.exe.log` (движок пишет подробный лог рядом со своим бинарником) видны те же строки плюс пер-пакетный `auto_strategy: <имя>-><хост>:<порт>`, если включён `--debug`. Полезные для разбора подстроки: `CONFIRMED`, `FAIL UDP`, `SWITCH`, `THROTTLE`, `SILENCE`.

## Чего профиль не должен делать

Чтобы судья видел весь поток, конфиг обязан отдавать этому экземпляру трафик целиком: узкий `--payload` должен стоять **после** строки `auto_strategy`, а сам монитор работает на `--payload=all` и `--in-range=a`. Иначе Lua увидит только ClientHello, не заметит троттлинг и никогда не выдаст `VALID`. Готовый пример такого устройства — `strategy_super_c.config` из актуального набора, а общий каркас — `configs/templates.config`.
