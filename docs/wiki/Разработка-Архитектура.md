# 🏗 Разработка: архитектура

Проект целиком на C++20-модулях: интерфейсы — `.cppm` (`export module <имя>;`), реализации — `.cpp` (implementation units с `module <имя>;` и `import` вместо `#include`). Заголовков и PCH нет, стандарт приходит через `import std;`. Стиль кода — `STYLE.md` в корне репозитория.

## Структура `src/`

| Каталог | Что это |
|---|---|
| `engine/` | точка входа `engine.exe`; интерфейс движка (`engine.api`), версия (`engine.version`), самозапрос прав, регистрация схемы UI |
| `core/` | база: `File`, `Debug`, `Localization`, `Service`, `hidden_process`, `service_diagnostics`, scheduler/thread_pool, utils |
| `ui/` | интерфейс на WebView2 через saucer: страницы, виджеты, локализация строк из `ui/text/*.list` |
| `unblock/` | логика обхода: `Unblock`, движки Zapret1/Zapret2, генерация стратегий, `DomainTesting`, `DNSHost`, `IPCSignals` (UDP 9999), `AppUpdater`, `TgProxy`, `helper_state` |
| `helper/` | `zapret_helper.exe`: UDP-сервер, curl-проверки, состояния хостов |
| `dom/` | тонкая обёртка DOM/WebView (element, view, events, geometry, tour) |
| `common/` | общее для движка и службы: `common.dns_config` (парсинг конфига прокси), `common.net_state` (детект VPN-туннеля) |
| `unblock_dns/` | `unblock_dns.exe`: хост AdGuard DnsLibs, смена DNS адаптеров, тело прокси |
| `unblock_update/` | `unblock_update.exe`: отдельный помощник обновления и удаления |
| `ext/` | обёртки сторонних библиотек и Win32 (цели `ext` и `win32`) |
| `ub_std`, `ub_version` | инфраструктура модулей: модуль стандартной библиотеки и модуль версии — отдельные цели, не каталоги |

`engine.api` вынесен в отдельную библиотеку `ub_engine_api`, а версия — в `ub_version`: исполняемый файл не может отдавать модульные файлы наружу, поэтому интерфейс движка и модуль версии живут статическими библиотеками.

## Соглашения модулей

- **Имя модуля — каталог плюс имя файла**, но каталог в имени не повторяется: файл `element.cppm` даёт `dom.element`, а не `dom.dom_element`. Интерфейс и реализация — один стем (`element.cppm` + `element.cpp`).
- Виджеты каталога `ui` — `ui.widget_<имя>` (все наследники `BaseElement`), остальные модули каталога — по смыслу (`ui.tutorial`).
- Интерфейс движка `IEngineAPI` лежит в `engine.api`, потому что его реализует движок, а не UI.
- У `dom`, `ui` и `unblock` есть умбреллы (`export import`) — `import ui;` даёт всё, что раньше давал `ui.h`.
- Исходники каталогов собираются глобом: `file(GLOB src_cpp CONFIGURE_DEPENDS "*.cpp")` и то же для `.cppm`; дальше `add_library(...)` и `FILE_SET CXX_MODULES`. Новый файл подхватывается на сборке, CMakeLists править не надо. Исключения — `helper` (там `main.cpp` принадлежит exe, отсекается фильтром), `engine` (в каталоге модули трёх таргетов, перечислены явно) и `src/ext` (curated-списки).

## Стандартная библиотека и `ext.*`

- Стандарт — `import std;`. Модуль собирает таргет `ub_std` из MSVC-шного `std.ixx` (детали и патч `cmake/MsvcStdModule.cmake` — в [Сборке и тестах](Разработка-Сборка-и-тесты)).
- Сторонние библиотеки (`ext.saucer`, `ext.coco`, `ext.curl`, `ext.bit7z`): заголовок в глобальном фрагменте модуля-обёртки (`module;` → `#include` → `export module …;`) плюс ручной реэкспорт имён. Список реэкспортируемых имён — это и есть поверхность, которую надо проверять при обновлении зависимости.
- Системные заголовки — отдельная цель `win32` (`ext.windows`): winsock2 обязательно до `windows.h`, весь набор Win32 наружу выходит `export using` и константами вместо макросов. Отдельная цель нужна, чтобы saucer/curl/bit7z не тянулись в таргеты, которым нужен только Win32. Внутри `ext.windows` есть `export import std;` — файл, импортирующий его, отдельно `import std;` не пишет.
- `import std` не отдаёт глобальные C-имена: пишем `std::uint32_t`, `std::FILE`, `std::fgets`/`std::strlen`. Глобальные `uint32_t` вне `<cstdint>` не гарантированы, поэтому C-ABI-обёртка `unblock_dns.ag_bind` реэкспортирует нужные имена.

Макросы через границу модуля не проходят вообще, поэтому текстуальными остаются только те заголовки, где иначе нельзя: `core/macros.hpp` и `ui/ui_macros.hpp`, генерируемый `engine/version.hpp` (нужен `engine.rc`), Catch2 в тестах и `tests/test_forwards.h`. Плюс глобальные фрагменты самих обёрток (`src/ext/*.cppm`, `unblock_dns/ag_bind.cppm`).

> [!WARNING]
> Форвард-декларация и `friend` на сущность из другого модуля не работают: `class X;` в модуле A и определение в модуле B — это разные типы (clang ругается `declaration attached to named module … cannot be attached to other modules`). Нужен `import`; для тестов — объявление харнесса в глобальном модуле (см. ниже).

## Тесты

Тесты каждого модуля — в `src/<module>/tests/`, свой exe (`test_helper`, `test_core`, `test_*` и т.д.). Тесты линкуют библиотеку модуля, а не компилируют его исходники: файлсет модулей принадлежит одному таргету (`helper` — статическая библиотека, `zapret_helper.exe` — только `main.cpp`; `test_unblock` линкует `unblock`). Catch2 подключается текстуально до импортов.

Доступ к приватным членам — `friend`-класс под `#ifdef HELPER_TESTS`/`UNBLOCK_TESTS` (макрос задаётся только при `BUILD_TESTS`). Класс-харнесс объявлен в `src/<module>/tests/test_forwards.h`, а сам заголовок включается в глобальном фрагменте тестируемого модуля и в тесте до импортов — иначе, как выше, friend и определение класса окажутся разными сущностями.

curl и zlib собираются статически из исходников (Schannel, HTTP-only), так что runtime-зависимостей и подмешивания `PATH` для `test_helper`/`zapret_helper` не нужно.

## Как это работает в рантайме

Движки запускаются как службы Windows через обёртку `SvcHost.exe`: `zapret1` крутит `winws.exe`, `zapret2` — `winws2.exe`, `zapret2_helper` — `zapret_helper.exe`, плюс служба DNS-прокси. Обмен между Lua, помощником и приложением — по UDP на localhost: `10000` — команды помощнику, `9999` — сигналы, снапшоты и логи обратно в `IPCSignals`.

Стратегии собираются `StrategyGenerator` (разворачивает шаблоны и плейсхолдеры) в набор аргументов, который `Zapret2Engine`/`Zapret1Engine` отдаёт службе. Итоговая команда целиком пишется в `logs/strategy.args.txt` — см. [Свои стратегии](Свои-стратегии).

## Где что искать при правке

| Задача | Куда смотреть |
|---|---|
| Точка входа, самозапрос прав, `--uninstall` | `src/engine/main.cpp` |
| Интерфейс страницы, виджеты | `src/ui/ui_*.cpp`, `src/ui/ui.widget_*.cppm` |
| Генерация стратегий и плейсхолдеры | `src/unblock/strategy_generator.cpp`, `strategy_config_base.cpp` |
| Модули движков Zapret1/2 | `src/unblock/zapret1_engine.cpp`, `zapret2_engine.cpp` |
| Адаптивный перебор (Lua) | `resources/lua/unblock_auto_strategy.lua` |
| Помощник | `src/helper/zapret_helper.cpp` |
| Диагностика служб | `src/core/service_diagnostics.cpp` |
| DNS-прокси | `src/unblock_dns/` |

Каталоги `ui/text/RU.list` и `US.list` — пользовательские строки: любой текст в интерфейсе идёт оттуда, ключи с префиксом `str_`. Эмодзи в строках логов и стектрейсов не используются (правила — в `STYLE.md`).

## Версионирование

Версия выводится из git и руками не правится. Значения приходят из модуля `engine.version` (`src/engine/version.cppm`, таргет `ub_version`): `VERSION_STR`, `VERSION_FULL`, `BUMP`, `RELEASE`, `DISTANCE`, `DIRTY`, `HASH`, `BASE_TAG`. Макросом остаётся только `VERSION_NUMBER` — его читает `engine.rc` как список через запятую. Полный разбор — в [Релиз и версии](Разработка-Релиз-и-версии).

## Навигация по коду

VS 2026 и расширение Microsoft C/C++ модули не понимают: в IntelliSense есть весь C++23, кроме модулей, а clangd в VS не встроен. Проект при этом конфигурится и собирается пресетами из VS нормально — не работает только IntelliSense. Навигация по модулям — clangd по `.clangd` и `_build/debug/compile_commands.json` (папка пресета `debug`, которым собирает IDE; агентская `_build_ai` тут ни при чём). Важно: clangd видит модули только после первой сборки — в свежесконфигуренном дереве modmap-файлы пустые, модульный граф CMake строит сканер во время сборки. В opencode LSP не работает, так что диагностика — компилятором (`scripts/build-ai.ps1`) и `scripts/tidy-ai.ps1`.
