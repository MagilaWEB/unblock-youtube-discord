# 📦 Разработка: релиз и версии

Версия в Unblock считается автоматически из состояния git. Руками её не правят никогда — ни в коде, ни в ресурсах.

## Как считается версия

За это отвечает `cmake/GetUnblockVersion.cmake`, подключаемый из корневого `CMakeLists.txt`. Схема — Conventional Commits плюс запасной вариант по значимости дифа:

1. **База** — свежий semver-тег `vX.Y.Z`, достижимый от `HEAD` (смотрятся только строго `vX.Y.Z`; нестандартные вроде `v1.4.6_fix` базой стать не могут).
2. **Скан `BASE..HEAD`**: `feat`/`fix` с `!` после типа или `BREAKING CHANGE:` в теле → MAJOR; иначе любой `feat:` → MINOR; иначе любой `fix:` → PATCH.
3. **Без Conventional Commits** — мерится значимость дифа: сумма добавленных и удалённых строк в текстовых файлах под `src/` и `cmake/` ≥ 20 → PATCH, иначе релиза нет и версия равна базе.
4. Бамп применяется к базе (`X+1.0.0`, `X.Y+1.0`, `X.Y.Z+1`, младшие части сбрасываются). **Точно на теге** (расстояние 0) версия равна тегу, релиза нет.

Тегирование само по себе версию не меняет: сборка впереди `vA` вычисляет `V`, и тег `vV` на том же коммите даёт пустой диапазон с базой `vV` — ту же `V`. Поэтому релизный тег ставится **после** сборки, и он обязан совпадать с вычисленной версией.

Что доступно наружу: `UNBLOCK_VERSION_TRIPLET`, `UNBLOCK_VERSION_STR`, `UNBLOCK_VERSION_NUMBER` (для `engine.rc`), `UNBLOCK_VERSION_FULL` (например `1.6.5+80.g64975e8-dirty`), `UNBLOCK_VERSION_DISTANCE`, `UNBLOCK_VERSION_BUMP`, `UNBLOCK_VERSION_RELEASE` (1, если тег нужно ставить), `UNBLOCK_VERSION_DIRTY`, `UNBLOCK_VERSION_HASH`, `UNBLOCK_VERSION_BASE_TAG`.

## Заголовок версии генерируется на сборке

`src/engine/version.hpp` (git-ignored) делается из `version.hpp.in` целью `unblock_version` через `cmake/WriteVersionHeader.cmake` — **на каждой сборке**, а не только на конфигурации. Перед пересчётом скрипт делает best-effort `git fetch --tags` (таймаут 30 с, без запроса логина), так что свежий тег, поставленный на другой машине или CI, подхватится. Файл перезаписывается только при смене содержимого — иначе каждая сборка дёргала бы mtime и пересобирала всех потребителей.

В C++ значения приходят константами модуля `engine.version` (`src/engine/version.cppm`, таргет `ub_version`). Макросы через границу модуля не проходят, поэтому каждый `VERSION_*` захватывается до `#undef` и переобъявляется константой с тем же именем. Макросом остаётся только `VERSION_NUMBER` — его читает `engine.rc` как список через запятую.

Вычисленная версия видна в логе: на конфигурации строка `UNBLOCK_VERSION = <full> (base … bump … release …)`, на сборке — `WriteVersionHeader: …`.

## Ручные рычаги

| Рычаг | Зачем |
|---|---|
| `scripts/build-ai.ps1 -VersionOverride X.Y.Z` | подставить версию без git-математики (тест апдейтера со «старой» инсталляцией). С такого билда тег ставить **нельзя** |
| `-DUNBLOCK_VERSION_BUMP_FORCE=major\|minor\|patch\|none` | принудительный бамп от текущей базы, автоопределение игнорируется |

Обход тихо живёт в кеше: `scripts/build-ai.ps1` форсит реконфиг на `-VersionOverride` и снимает застрявший override (`-UUNBLOCK_VERSION_OVERRIDE`), если флаг не передан.

## Порядок выпуска

1. **Собрать релиз**: `pwsh -NoProfile -File scripts/release-ai.ps1`. По умолчанию он гонит `release-min` (без тестов), затем упаковывает payload и установщик. Посмотреть на вычисленную версию — в логе сборки.
2. **Поставить тег** `v<триплет>` на этот коммит — только если вычисленная версия совпала с ожидаемой (в логе `release 1`). Версия тега обязана равняться `VERSION_STR`.
3. **Опубликовать GitHub-релиз** с двумя ассетами: `unblock.7z` (payload) и `unblock-setup.exe` (установщик).

## Что кладётся в релиз и как

`scripts/release-ai.ps1` собирает `release-min`, находит `7za.exe` в `_build_ai/7za/x64` и проверяет, что `bin/` не от debug-сборки: если там есть `.pdb`, скрипт откажется паковать (иначе `-SkipBuild` после debug-сборки тихо выпустил бы debug в релиз).

Payload — строго фиксированной раскладки, потому что апдейтер ищет внутри `unblock/bin/engine.exe`:

```
unblock/  ← bin/ + binaries/ + configs/ + ui/ + LICENSE.txt + README.md
```

Из архива выбрасываются `test_*`, `.pdb` и `.log` — ничего от дев-сборки в релиз не протекает, а `user/` и `logs/` в payload не входят никогда. Архив пакуется из staging-каталога (`7za a -t7z -mx=9 -mf=off unblock`), поэтому внутри лежит ровно `unblock\…`.

Установщик — `installer/unblock.iss` (Inno Setup 6). `scripts/release-ai.ps1` берёт версию из `ProductVersion` готового `bin\engine.exe` и зовёт `ISCC` с `/DAppVersion=…`; без установленного Inno Setup шаг пропускается, а `unblock.7z` всё равно остаётся. Установщик **онлайн**: он качает `unblock.7z` с последнего релиза GitHub в момент установки и распаковывает встроенными средствами Inno (никакой внешний `7za.exe` не нужен). При обновлении поверх прошлой версии он удаляет `bin/`, `binaries/`, `configs/`, `ui/`, а `user/` и `logs/` оставляет; при удалении зовёт `engine.exe --uninstall` и дополнительно страхуется `sc stop`/`sc delete` и сбросом TCP-таймстампов.

## Обновление из приложения

Приложение не подменяет себя само. Оно проверяет `releases/latest`, качает `unblock.7z` последнего релиза, распаковывает во временный каталог и запускает оттуда `unblock_update.exe`. Тот дожидается завершения старого движка (с тройной проверкой: PID, отсутствие нашего `engine.exe`, доступность `bin\engine.exe` на запись), вычищает управляемые каталоги (`bin`, `binaries`, `ui` — чтобы удалённые в новой версии файлы не остались мусором), копирует payload, **не трогая** `user/` и `logs/`, и запускает свежий движок. Журнал — `%TEMP%\unblock_update.log`. Апдейтер ожидает внутри архива `unblock/bin/engine.exe` — отсутствие этого файла считается битым обновлением и останавливает процесс, чтобы он не выглядел как «обновление ничего не сделало».

## Требования к машине релиза

- Установленный LLVM/clang и Ninja — как для обычной сборки, и `release-min` должен собираться без тестов.
- `_build_ai/7za/x64/7za.exe` — упаковщик берётся из собранных зависимостей (появится после первой конфигурации).
- Inno Setup 6 (`ISCC.exe`) — для установщика. Скрипт сам ищет его в `%LOCALAPPDATA%\Programs\Inno Setup 6`, `Program Files (x86)`, `Program Files` и в `PATH`. Без него `unblock.7z` соберётся, а `unblock-setup.exe` просто не появится (в логе будет подсказка `winget install JRSoftware.InnoSetup`).

## Чек-лист выпуска

1. Убедиться, что рабочее дерево чистое, а теги подтянуты (`git fetch --tags`) — версия считается от них.
2. `pwsh -NoProfile -File scripts/release-ai.ps1` — сборка `release-min` и упаковка.
3. В логе сборки найти `UNBLOCK_VERSION = <full> (base … bump … release …)`. Если `release 0`, тег ставить нечего: значимость дифа не дотянула до релиза (либо вы ровно на теге).
4. Поставить тег `v<триплет>` на коммит — он должен совпасть с `VERSION_STR`.
5. Опубликовать GitHub-релиз и приложить `release/unblock.7z` и `release/unblock-setup.exe`.
6. Проверить обновление «из приложения» на старой версии: она должна увидеть новый релиз и поставить его, сохранив `user/` и `logs/`.

Для проверки самого апдейтера без выпуска есть `-VersionOverride X.Y.Z` — им можно притвориться старой установкой. Тег с такого билда не ставится.

Тег и релиз создаются вручную — `scripts/release-ai.ps1` их не ставит и не публикует.
